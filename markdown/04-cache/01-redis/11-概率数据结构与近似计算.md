# 概率数据结构与近似计算

Redis 不仅支持精确集合和计数，还包含一类高性能的“近似数据结构”。它们的目标不是百分百准确，而是用极低内存换取“足够精确”的统计能力，尤其适合大规模实时流量统计、去重、过滤和分位数分析。

注意：

- HyperLogLog 是 Redis 内置能力。
- Bloom Filter、Cuckoo Filter、Count-Min Sketch、Top-K 和 t-digest 通常需要启用 RedisBloom / Redis Stack 模块。
- 这类结构的核心是“误差可控”，对业务允许一定误差的场景非常合适。

## 1. HyperLogLog

### 适用场景

- 统计 UV、DAU、独立设备数、去重点击数、不同 IP 访问数。
- 适合海量日志流的“去重估算”，而不是需要精确唯一值列表。
- 典型场景：广告投放曝光 UV、页面访问去重、接口调用去重、日志采样去重。

### 使用 Demo

```bash
# 统计某天页面 UV
redis-cli
127.0.0.1:6379> PFADD app:uv:2026-08-19 user:10001 user:10002 user:10003 user:10001
(integer) 1
127.0.0.1:6379> PFADD app:uv:2026-08-19 user:10004 user:10005
(integer) 1
127.0.0.1:6379> PFCOUNT app:uv:2026-08-19
(integer) 5

# 多个 HLL 合并
127.0.0.1:6379> PFADD app:uv:2026-08-18 user:20001 user:20002
(integer) 1
127.0.0.1:6379> PFMERGE app:uv:2026-08-19:all app:uv:2026-08-18 app:uv:2026-08-19
127.0.0.1:6379> PFCOUNT app:uv:2026-08-19:all
```

Python 示例：

```python
import redis
r = redis.Redis(host='127.0.0.1', port=6379, decode_responses=True)

r.pfadd('uv:day:2026-08-19', 'u1', 'u2', 'u3', 'u1')
r.pfadd('uv:day:2026-08-19', 'u4', 'u5')
print(r.pfcount('uv:day:2026-08-19'))  # 近似去重结果
```

### 实现原理

HyperLogLog 不是保存所有元素，而是估算基数。

- 对每个元素做 64 位哈希。
- 取哈希值的前 `p` 位作为寄存器编号，后面位用来计算“连续 0 的个数”。
- 例如某个元素哈希值为 `101100...`，从第一个 1 出现的位置计算前导零数（leading zeros），记录到对应寄存器。
- 每个寄存器保存当前看到的最大前导零数；最终基数估计来自所有寄存器的汇总。
- Redis 的 HLL 是定长内存结构，通常很小，适合超大数据去重。

关键特征：

- 优点：极小内存、速度快、支持合并。
- 缺点：只能估算，不是精确集合；误差约为 `1.04 / sqrt(m)`，`m` 是寄存器数。
- 用途：`PFCOUNT` 相比 `SET` 更省内存，但牺牲精度。

### 设计要点

- 用于“知道大概有多少个不同元素”，不需要枚举元素。
- 不适合做“精确删除、遍历、取出具体值”的场景。
- 如果需要精确唯一值、必须用 Set 或数据库去重。

## 2. Cuckoo Filter

### 适用场景

- 判断某个元素“是否可能存在”，例如：
  - 黑名单过滤：请求 URL 是否在扩展黑名单中。
  - 垃圾邮件/恶意 IP 判断。
  - 反作弊/重复请求检测。
  - 过滤缓存未命中或热点 key。
- 比 Bloom Filter 更适合支持删除，并且在某些场景中更紧凑，常用于高性能在线过滤。

### 使用 Demo

先准备 Redis Stack 或 RedisBloom：

```bash
docker run -d --name redis-stack -p 6379:6379 redis/redis-stack:latest
```

CLI 示例：

```bash
redis-cli
127.0.0.1:6379> CF.RESERVE my_cuckoo 100000 0.01
OK
127.0.0.1:6379> CF.ADD my_cuckoo user:1001
(integer) 1
127.0.0.1:6379> CF.ADD my_cuckoo user:1002
(integer) 1
127.0.0.1:6379> CF.EXISTS my_cuckoo user:1001
(integer) 1
127.0.0.1:6379> CF.EXISTS my_cuckoo user:9999
(integer) 0
127.0.0.1:6379> CF.DEL my_cuckoo user:1001
(integer) 1
```

Python 示例：

```python
import redis
r = redis.Redis(host='127.0.0.1', port=6379, decode_responses=True)

r.execute_command('CF.RESERVE', 'cf:emails', 100000, 0.01)
print(r.execute_command('CF.ADD', 'cf:emails', 'a@site.com'))
print(r.execute_command('CF.EXISTS', 'cf:emails', 'a@site.com'))
print(r.execute_command('CF.EXISTS', 'cf:emails', 'b@site.com'))
```

### 实现原理

Cuckoo Filter 与 Bloom Filter 都是概率过滤器，但插入方式不同。

- 过滤器内部是多个 bucket，每个 bucket 放若干指纹（fingerprint）。
- 插入时，计算元素哈希，得到两个候选位置：`h1(x)` 和 `h2(x)`。
- 过滤器会尝试把元素指纹放入其中一个 bucket；若 bucket 已满，则“踢出”一个旧指纹，将其重定位到另一个候选位。
- 这种“鸠占鹊巢”式挪动，让元素的存储位置不固定，因此能更高效利用空间。
- 查询时只检查两个候选位置是否存在同样指纹。

优点：

- 比 Bloom Filter 支持删除。
- 对相同容量，通常比 Bloom 更节省空间。
- 查找速度快，缓存友好。

缺点：

- 仍然存在误判：元素不在集合内，但很可能被判定为存在。
- 负载过高时可能触发踢出和重定位，导致插入失败。

### 设计要点

- 如果过滤业务要求“永远不误删、可删除”，Cuckoo Filter 是一个不错的选择。
- 当元素需要高压缩比和支持删除时，优先考虑 Cuckoo Filter。
- 它“不是完全准确”，适合做前置过滤，不能替代数据库唯一约束。

## 3. Bloom Filter

### 适用场景

- 判断某个元素是否“可能存在”。
- 典型场景：
  - 缓存穿透防护：先判断 key 是否值得查询数据库。
  - 黑名单/白名单过滤：判断 IP、URL、设备号是否在名单中。
  - 反垃圾系统：过滤重复恶意请求。
  - AI/日志中判断某个事件是否曾经出现过。

### 使用 Demo

```bash
redis-cli
127.0.0.1:6379> BF.RESERVE my_bloom 1000000 0.01
OK
127.0.0.1:6379> BF.ADD my_bloom user:1001
(integer) 1
127.0.0.1:6379> BF.ADD my_bloom user:1002
(integer) 1
127.0.0.1:6379> BF.EXISTS my_bloom user:1001
(integer) 1
127.0.0.1:6379> BF.EXISTS my_bloom user:9999
(integer) 0
```

批量插入：

```bash
127.0.0.1:6379> BF.MADD my_bloom user:2001 user:2002 user:2003
1) (integer) 1
2) (integer) 1
3) (integer) 1
```

Python 示例：

```python
import redis
r = redis.Redis(host='127.0.0.1', port=6379, decode_responses=True)
r.execute_command('BF.RESERVE', 'bf:users', 1000000, 0.01)
print(r.execute_command('BF.ADD', 'bf:users', 'user:1001'))
print(r.execute_command('BF.EXISTS', 'bf:users', 'user:1001'))
print(r.execute_command('BF.EXISTS', 'bf:users', 'user:9999'))
```

### 实现原理

Bloom Filter 由一个很大的位数组和多个哈希函数组成。

- 插入元素 `x` 时，对 `x` 计算 `k` 个哈希值。
- 把对应 bit 数组位置设置为 1。
- 查询元素是否存在时，再做同样的 `k` 个哈希，检查这些位是否都为 1。
- 若任一位为 0，则一定不在集合中。
- 若所有位都为 1，则“可能存在”，这就会有误判：也就是“False Positive”。

Bloom 的实现特点：

- 误判率通过位数组大小和哈希函数个数控制。
- 不能删除：因为一个 bit 可能被多个元素共享，删除会误伤其他元素。
- 空间效率极高：比完整集合存储方式更省内存。

### 设计要点

- 适合做“快速前置判定”，不能做业务唯一性校验。
- 常用于缓存穿透过滤：在访问数据库前先问 Bloom，避免海量无效 key 打到 DB。
- 如果需要“删除元素”，可考虑 Cuckoo Filter。

## 4. Count-Min Sketch

### 适用场景

- 高频词统计、热搜词判断、异常事件计数、高频 IP、热门商品统计。
- 适合在海量数据下估算某个元素出现次数，通常不要求完全精确。
- 非常适合流式计算中的“估算计数”，例如实时日志中统计某个 URL 的访问次数。

### 使用 Demo

```bash
redis-cli
127.0.0.1:6379> CMS.INITBYPROB my_cms 0.001 0.01
OK
127.0.0.1:6379> CMS.INCRBY my_cms user:1001 5 user:1002 3 user:1001 2
1) (integer) 7
2) (integer) 3
3) (integer) 7
127.0.0.1:6379> CMS.QUERY my_cms user:1001 user:1002 user:1003
1) (integer) 7
2) (integer) 3
3) (integer) 0
```

Python 示例：

```python
import redis
r = redis.Redis(host='127.0.0.1', port=6379, decode_responses=True)
r.execute_command('CMS.INITBYPROB', 'cms:urls', 0.001, 0.01)
print(r.execute_command('CMS.INCRBY', 'cms:urls', 'url:/home', 5))
print(r.execute_command('CMS.QUERY', 'cms:urls', 'url:/home'))
```

### 实现原理

Count-Min Sketch 本质上是一个二维计数矩阵：

- 有 `d` 行，每行对应一个哈希函数。
- 每行有 `w` 个计数器。
- 插入元素 `x` 时，把 `x` 经过 `d` 个哈希函数映射到某些计数器上，然后加 1。
- 查询时，还是用同样的 `d` 个哈希函数定位到对应计数器，取最小值作为估计值。

原因：

- 不同元素可能碰撞到同一个位置。
- 但取 `d` 个位置的最小值，能控制“误差”在可接受范围内。
- Count-Min Sketch 的估计满足：`estimate(x) >= true_count(x)`，永远不低估，可能高估。

优点：

- 适合大规模流式计数。
- 只保留估计值，内存远小于精确计数器。
- 适合高频元素和近似热度分析。

缺点：

- 不能做精确计数。
- 误差来自哈希冲突，不能反向恢复精确频率。
- 主要是“估计，非精确”。

### 设计要点

- 适合“计算某个 key 的大概出现次数”，而非“精确的全量计数”。
- 典型场景：实时排名、热度估算、日志聚合、错误码统计。
- 用于有明显大头效应且允许误差的场景。

## 5. Top-K

### 适用场景

- 实时热门商品、热点搜索词、最活跃接口、最频繁访问 URL。
- 流式实时新闻热榜、推荐系统的热度挖掘、事件热度看板。
- 常用于“在海量事件中找出前 K 个最频繁元素”。

### 使用 Demo

```bash
redis-cli
127.0.0.1:6379> TOPK.RESERVE topk:keywords 10 2000 7 0.925
OK
127.0.0.1:6379> TOPK.ADD topk:keywords "java" "redis" "mysql" "redis" "java" "java" "kafka" "redis" "mybatis"
1) (integer) 1
2) (integer) 1
3) (integer) 1
4) (integer) 1
5) (integer) 1
6) (integer) 1
7) (integer) 1
8) (integer) 1
9) (integer) 1
127.0.0.1:6379> TOPK.LIST topk:keywords WITHCOUNT
1) "java"
2) "redis"
3) "mysql"
4) "kafka"
5) "mybatis"
```

Python 示例：

```python
import redis
r = redis.Redis(host='127.0.0.1', port=6379, decode_responses=True)
r.execute_command('TOPK.RESERVE', 'topk:words', 10, 2000, 7, 0.925)
for w in ['java', 'redis', 'mysql', 'redis', 'java', 'java', 'kafka', 'redis', 'mybatis']:
    print(r.execute_command('TOPK.ADD', 'topk:words', w))
print(r.execute_command('TOPK.LIST', 'topk:words', 'WITHCOUNT'))
```

### 实现原理

Top-K 通常不是简单的全量排序，而是近似热度算法。

- 维护一个小规模的候选集（优先级队列或 Top-K 堆）。
- 每次新元素到来时，更新其计数。
- 若计数足够大，候选元素进入 Top-K；若计数较低，则被淘汰。
- 近似算法通常通过“损失性计数器+堆维护”来降低内存成本。

RedisBloom 的 Top-K 设计思路：

- 在很大数据流里，维持一个固定大小的 Top-K 集合。
- 不需要保存完整计数表，只保存候选元素和近似频次。
- 适合高频热词分析，但不保证绝对精确排序。

优点：

- 内存稳定，适合高吞吐流式场景。
- 适合看“当前最热”而非完整统计信息。

缺点：

- 结果是近似热榜，存在边界元素可能被误判。
- 适合业务看板，不适合做最终结算、精确发票统计等场景。

### 设计要点

- 适合“热点发现”，不适合“精确全量排名”。
- 与 Count-Min Sketch、Bloom Filter 经常组合使用：
  - Bloom：过滤已知项。
  - CMS：估算频次。
  - Top-K：提取热门 key。

## 6. t-digest

### 适用场景

- 近似分位数统计：P50、P95、P99、最大值、最小值。
- 延迟分布分析：接口延迟、数据库查询耗时、网络 RTT、业务耗时分布。
- 监控中心需要看“95% 请求小于多少 ms”，而不想保留全部样本。

### 使用 Demo

```bash
redis-cli
127.0.0.1:6379> TDIGEST.CREATE latency 100
OK
127.0.0.1:6379> TDIGEST.ADD latency 20 30 35 40 80 120 500 1000
(integer) 8
127.0.0.1:6379> TDIGEST.QUANTILE latency 0.5 0.95 0.99
1) "40"
2) "500"
3) "1000"
```

Python 示例：

```python
import redis
r = redis.Redis(host='127.0.0.1', port=6379, decode_responses=True)
r.execute_command('TDIGEST.CREATE', 'td:latency', 100)
for v in [20, 30, 35, 40, 80, 120, 500, 1000]:
    r.execute_command('TDIGEST.ADD', 'td:latency', v)
print(r.execute_command('TDIGEST.QUANTILE', 'td:latency', 0.5, 0.95, 0.99))
```

### 实现原理

t-digest 是一种近似分位数算法，属于“聚类型摘要”。

- 它把大量样本压缩成一组“中心点（centroid）”。
- 每个 center 记录：
  - 均值（mean）
  - 总权重（count）
  - 可能的最小值/最大值信息
- 新样本按顺序插入到适合的 centroid 中，或者需合并相邻 centroid。
- 在查询分位数时，按累计权重进行近似插值即可得到 P50、P95、P99 等值。

t-digest 与传统直方图最关键的区别：

- 传统直方图固定 bucket，可能导致极端尾部压缩过严重。
- t-digest 通过可变中心和权重更灵活地表达尾部分布。

优点：

- 空间占用远低于保留所有样本。
- 对高延迟尾部数据更友好，适合监控和观测。
- 非常适合“高吞吐系统里看延迟分布”。

缺点：

- 它也是近似算法，不能像精确排序数组那样得到完全精确分位数。
- 对非常极端分布，估计误差仍需关注。

### 设计要点

- 当你需要“知道大多数请求在什么区间内”而不是所有样本时，t-digest 非常合适。
- 适合分布式追踪、性能看板、接口 SLA 监控。
- 关注 P99、P999 等场景时，它比简单平均值更有价值。

## 实战选择建议

1. 需要统计“不同元素多少个”？
   - HyperLogLog：最适合 UV、去重估算。

2. 需要判断“某元素是否可能存在”？
   - Bloom Filter：适合缓存穿透过滤、黑名单控制。
   - Cuckoo Filter：适合需要支持删除的过滤场景。

3. 需要近似计数？
   - Count-Min Sketch：适合热度、访问量估计。

4. 需要找 Top K 热点？
   - Top-K：适合热门商品、关键词、接口。

5. 需要近似分位数？
   - t-digest：适合延迟分布、监控分析。

## 一个通用思路

在真实业务中，这些概率数据结构通常不是独立使用，而是组合：

- Bloom Filter：先过滤明显不可能的 key。
- HyperLogLog：统计总去重规模。
- Count-Min Sketch：估算元素近似访问次数。
- Top-K：检测实时热点。
- t-digest：展示延迟分布和 SLA。

这样能在不牺牲太多准确性的前提下，极大减少内存开销和计算成本。

## 总结

Redis 中的概率数据结构本质上都是“用少量内存换取近似答案”，它们非常适合：

- 大规模去重
- 热点发现
- 过滤未命中
- 监控分位数
- 流式统计

但必须建立明确边界：

- 这些结构解决的是“近似统计”，不是“精确数据管理”。
- 如果业务要求强一致性、精确去重、完整查询结果，就不能只依赖概率结构。

在工程上，最佳实践是：用概率结构做“估算和过滤”，用数据库、缓存和索引做“最终准确答案”。
